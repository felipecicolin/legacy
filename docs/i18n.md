# i18n — a fundação pt-BR

> Locale da aplicação: [`config/locales/pt-BR.yml`](../config/locales/pt-BR.yml)
> · Formatos: [`config/locales/rails.pt-BR.yml`](../config/locales/rails.pt-BR.yml)
> · Nomes de campo: [`config/locales/models/pt-BR.yml`](../config/locales/models/pt-BR.yml)
> · Specs: [`spec/i18n_spec.rb`](../spec/i18n_spec.rb)
> · [`spec/models/enum_translation_audit_spec.rb`](../spec/models/enum_translation_audit_spec.rb)

O `AGENTS.md` já diz a regra que a CI cobra: todo texto visível passa por
`t()`. Este documento é o outro lado — o texto que **não** é nosso, a
convenção de nomes que as issues de modelo vão seguir, e por que cada número
aqui é o que é.

## Por que a gem

`config/application.rb` já declarava `default_locale = "pt-BR"`, mas isso só
diz em que idioma procurar. Quem tem as traduções do próprio framework é a
`rails-i18n`, e sem ela o miolo do Rails responde em inglês:
`"can't be blank"`, `"March"`, `"$184,000.00"`, `"3 months"`.

O detalhe que torna isso caro é que **nenhum dos três linters de i18n pega**.
O `DecorateString` do rubocop e o `no-hardcoded-string` do herb procuram
string literal no nosso código; o `bin/i18n-tasks health` compara as nossas
chaves com as nossas buscas. Texto que sai de dentro de uma gem é invisível
para os três — aparece na tela e em lugar nenhum antes disso.

Por isso o gate desta camada é spec, não linter: `spec/i18n_spec.rb` afirma o
resultado formatado, string por string.

## O que a gem entrega e o que ainda definimos

Medido com a `rails-i18n` 8.1 no locale `pt-BR`:

| O que | Sai assim | Origem |
| --- | --- | --- |
| `I18n.l(date)` | `12/03/2026` | rails-i18n |
| `I18n.l(date, format: :long)` | `12 de março de 2026` | rails-i18n |
| `number_to_currency(184_000.0)` | `R$ 184.000,00` | rails-i18n |
| `number_with_delimiter(1_234_567.89)` | `1.234.567,89` | rails-i18n |
| `distance_of_time_in_words(90.days)` | `3 meses` | rails-i18n |
| `errors.messages.blank` | `não pode ficar em branco` | rails-i18n |
| `number_to_percentage(62)` | `62%` | **nosso** |
| Nome de campo em mensagem de erro | `E-mail`, `Senha` | **nosso** |

Duas observações que economizam uma investigação:

**A data "curta" que se quer é a `:default`, não a `:short`.** Na rails-i18n
`date.formats.short` é `"%d de março"` — dia e mês, sem ano. O formato
`12/03/2026` é o `:default`. Renomear os formatos da gem para casar com o
nosso vocabulário seria trocar uma convenção que todo mundo conhece por uma
que só existe aqui; a escolha foi usar `:default` e `:long` como estão.

**Percentual precisa de correção porque a precisão vem do Rails, não do
locale.** O default é `precision: 3`, então `62` sairia `62,000%`. A correção
é `precision: 2` com `strip_insignificant_zeros: true`, e não `precision: 0`:
com precisão zero, `62.5` viraria `63%` — o formato passaria a arredondar
dado. Com o strip, `62` dá `62%` e `62.5` dá `62,5%`.

## Um locale só, declarado

```ruby
config.i18n.available_locales = ["pt-BR"]
```

A `rails-i18n` empurra `I18n.available_locales` de um para ~140. Declarar o
único locale do produto faz duas coisas: o `store_translations` descarta na
carga tudo que não é `pt-BR`, e um `I18n.locale = :fr` levanta
`I18n::InvalidLocale` em vez de servir a tela em francês. Quando existir um
segundo idioma de verdade, ele entra nesta lista — que é onde se procura.

## Onde cada chave mora

O roteador do `config/i18n-tasks.yml.erb` decide o arquivo pelo prefixo da
chave, e o `bin/i18n-tasks normalize` **move** o que estiver fora do lugar.
Escrever no arquivo errado não dá erro na hora: dá diff depois.

| Prefixo | Arquivo |
| --- | --- |
| `activerecord.*`, `activemodel.*` | `config/locales/models/pt-BR.yml` |
| `date.*`, `time.*`, `number.*`, `errors.*`, `helpers.*`, `support.*` | `config/locales/rails.pt-BR.yml` |
| `<nome>_component.*` | `app/components/<nome>_component/<nome>_component.pt-BR.yml` |
| todo o resto | `config/locales/pt-BR.yml` |

Subdiretório funciona: o Rails carrega `config/locales/**/*.yml`, então
`models/pt-BR.yml` entra sem nenhuma configuração extra.

## Convenção de nomes

Fixar isto agora custa uma tabela. Fixar depois de 500 chaves custa uma
migração.

| Para que | Chave |
| --- | --- |
| Nome de um campo | `activerecord.attributes.<modelo>.<campo>` |
| Mensagem de erro específica de um campo | `activerecord.errors.models.<modelo>.attributes.<campo>.<tipo>` |
| Texto de view, action ou componente | chave preguiçosa: `t(".titulo")` |
| Vocabulário resolvido em runtime | `statuses.*`, `skills.*`, `countries.*` |

**Chave preguiçosa em view e componente não é preferência de estilo:** o
`Rails/I18nLazyLookup` do rubocop cobra, e ela é o que faz o scanner do
i18n-tasks casar a chave com a busca. Uma chave absoluta numa view abre a
porta para órfã silenciosa.

**Vocabulário resolvido em runtime é o único caso de chave que o scanner não
enxerga.** `t("statuses.#{obra.status}")` não tem literal para procurar, então
as entradas apareceriam como órfãs. A saída é o comentário ao lado da chamada:

```erb
<%# i18n-tasks-use t('statuses.*') %>
<%= t("statuses.#{obra.status}") %>
```

E **nunca** uma entrada genérica em `ignore_unused`: a diferença é que o
comentário fica ao lado do código que o justifica, e o `bin/directive_guard`
conta cada um — o `.directive_allowlist` precisa ganhar a linha
correspondente, com revisão. Uma entrada no `ignore_unused` apaga a categoria
inteira de uma vez e nunca mais é revisitada.

## Enum na UI

**Nenhum valor de enum vai cru para a tela.** `"draft"` não é texto de
produto; é chave.

A convenção é uma só: o rótulo de um enum é a chave `<enum no plural>.<valor>`
no topo do locale.

```ruby
class Project < ApplicationRecord
  enum :status, { draft: 0, published: 1 }
end
```

```yaml
pt-BR:
  statuses:
    draft: Rascunho
    published: Publicada
```

Duas consequências que valem dizer em voz alta:

- **O vocabulário é compartilhado, e é assim de propósito.** `statuses.draft`
  vale para qualquer modelo cujo enum se chame `status`. Se dois modelos
  precisam de vocabulários diferentes, é sinal de que os enums não são a mesma
  coisa e não deviam ter o mesmo nome — `project_status` e `invoice_status`,
  cada um com o seu `project_statuses.*` / `invoice_statuses.*`.
- **O rótulo não entra em `activerecord.attributes`.** Lá mora o nome do
  *campo* (`status: Situação`); aqui, o nome do *valor*. Misturar os dois faz
  a chave depender do modelo, e o vocabulário deixa de ser reutilizável.

### O guarda, e por que ele não é um `it` de três linhas

`spec/models/enum_translation_audit_spec.rb` percorre os modelos e reprova
qualquer valor de enum sem rótulo. Hoje nenhum modelo tem enum, e é justamente
por isso que ele foi escrito com cuidado:

- **`Rails.application.eager_load!` antes de tudo.** No ambiente de teste o
  autoload só carrega o que alguém referenciou, então
  `ApplicationRecord.descendants` vem vazio. Sem essa linha o spec passaria
  hoje, passaria depois do primeiro enum sem rótulo, e passaria para sempre —
  é a mesma família de falha das quatro "ferramenta que sai zero em silêncio"
  do `AGENTS.md`.
- **A auditoria vive em `spec/support/enum_translation_audit.rb`, fora do
  exemplo.** Isso permite chamá-la com um modelo falso e verificar que ela
  *reprova*. Um guarda que só roda sobre conjunto vazio é uma afirmação sem
  evidência; este prova a si mesmo antes de a primeira issue de modelo chegar.

## Armadilhas

**Comentário em arquivo de locale não sobrevive.** O `bin/i18n-tasks normalize`
reescreve o YAML a partir da árvore carregada, e comentário não está na
árvore. Explicação sobre uma chave vai aqui, ou no código que a usa.

**`password_digest` e `password` têm o mesmo rótulo, e o erro sai duplicado.**
`User` valida a presença dos dois — o virtual, pelo `has_secure_password`, e a
coluna, porque o `database_consistency` cobra a `NOT NULL`. Ambos são "Senha"
para quem lê, então `errors.full_messages` de um `User` vazio traz a mesma
frase duas vezes. Nenhuma view renderiza `full_messages` hoje; quando alguma
renderizar, o lugar de resolver isso é a view (`full_messages_for` no campo do
formulário), não um rótulo inventado para a coluna.

**Chave nova em arquivo novo pede `bin/i18n-tasks normalize` antes do commit.**
O `health` reprova arquivo não normalizado, e a ordem alfabética que ele
espera não é a ordem em que se escreve.
